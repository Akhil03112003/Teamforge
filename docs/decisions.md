Implementation choices within approved rules: reusable32-byte SecureRandom invitation codes, SHA-256-only persistence, database24h expiry, one unrevoked generation/team and rotation under team lock. Plaintext is never persisted, including in idempotency records. Generation is deliberately unkeyed because plaintext is shown only once; lost issuance requires explicit rotation. Public redemption is keyed and calls shared admission with validated Invitation authority. Acceptance is keyed and uses RequestApproval; it retains the documented200 id/state response and adds membership details. IdempotentMutations now records the caller-specified success status (existing default201 unchanged).

PENDING transitions only to ACCEPTED/DECLINED/WITHDRAWN/CLOSED. Full acceptance leaves pending; duplicate pending creation returns existing intent without duplicate audit; new requests after resolution are allowed if eligible. Entry through create/invite/approval resolves other event-pending requests. Cleanup takes ordered subordinate rows under the applicant anchor without locking other teams; rotation takes team before invitations. Nested retryable SQL errors reach the root runner so whole-workflow retry remains possible. No business admission bypass is introduced.

Listing uses bounded100-item UUID cursor pages; UI supports loading more. Invitation attempt limit default60/account/min and600/direct-IP/min, bounded20000 tracked keys, configurable account threshold. This is single-instance and must be reviewed for hosting replicas/trusted proxies during hardening. Audit authorization is restricted to actual membership evidence; request actions alone do not grant full team-history access.

These choices resolve earlier proposed invite reuse, request transitions/cleanup and admission rate defaults for M4. Existing indefinite idempotency retention remains; no token recovery or silent key expiration. Hosting/free-tier verification, operational retention, scoring, SSE and remaining delivery gates stay open. Final Java21 clean verify passed133 tests (45 new M4), zero failures/errors/skips; frontend checks passed. Public50-way invitation race produced1 success/49 capacity conflicts with no ordinary database deadlocks/timeouts. Actual verification/limitations: [verification-m4.md](verification-m4.md). ## M3 implementation record — 2026-11-09
The user authorized shared admission, persisted create/admission idempotency and actual PostgreSQL races, without M4 workflows. Baseline 61 tests passed before changes. This section supersedes M2 statements that keys are not required or replay is deferred.

Implemented within the approved architecture: shared MembershipAdmissionService; internal sealed LeaderApproval authority checked under the team lock; creator uses the same append checks. There is no direct-join endpoint, test-only route, invite/request workflow, new dependency or infrastructure. READ COMMITTED root mutations retain anchor NO KEY UPDATE before team FOR UPDATE; keyed claims precede both. Lifecycle mutations use the same bounded transaction runner. Existing unique/composite/deferred/capacity constraints remain authoritative.

V4 persists caller/operation/key, canonical SHA-256 fingerprint and successful 201 JSON result atomically with mutation/audit. Keyed create is now mandatory; the frontend reuses its pending intent key. Failed work rolls back the key; anomalous committed IN_PROGRESS conflicts without takeover. Completed records remain indefinitely, including deleted resources; no cleanup policy is silently assumed. Future retention/operational recovery requires review. Lock/statement/transaction defaults are 5/15/30 seconds; three root attempts handle identified rolled-back transient conflicts, with no fragment retry or blind retry after connection loss.

Docker remains unavailable, so genuine native PostgreSQL18.6 was used with independent connections, not mocked locks. Three 50-contender races and deliberate deadlock/timeout recovery passed within the final 88-test Java21 verify. PostgreSQL18 Flyway compatibility warning remains a documented limitation; CI17.7 and remote GitHub Actions were not run. Free-tier deployment selection remains open. M4 must add transactional request/invite authorization and consumption to this admission service; its HTTP admission race coverage remains future work.

## M2 team lifecycle implementation — 2026-11-09
Latest user scope moves team lifecycle into M2 and reserves persisted idempotency/concurrency acceptance for M3. M1 was reverified first: Java 21 clean verify passed all 34 tests. Initial working tree was clean. No team admission, invite, request, SSE or suggestion endpoint is added.
V3 adds event_participants lock anchors, teams, team_members and immutable audit_events without editing V1/V2. The approved logical memberships table is concretely named team_members as requested. Team leader membership is a deferred composite FK, so every active team has a valid member leader at commit. Snapshot audit identifiers intentionally have no cascading active-domain FKs.
TeamStore uses JdbcTemplate for explicit SQL locks/deferred-FK lifecycle inside Spring's existing transaction manager; identity/profile persistence stays JPA. This is a data-access choice within the modular monolith, not a new datastore/dependency. Outer rollback integration coverage verifies that JDBC team/member/anchor/audit writes roll back together.
Lock protocol: ensure/lock affected (hackathon,user) anchors first using FOR NO KEY UPDATE, then lock team rows FOR UPDATE, with ascending IDs when multiple rows are involved. Anchor keys never change. NO KEY UPDATE still serializes membership changes while remaining compatible with FK key-share checks during succession; FOR UPDATE on those anchors could introduce a preventable wait cycle with successor references. See PostgreSQL explicit-locking documentation. No successor-anchor lock is acquired after a team lock. Every departure/removal rechecks current membership/leadership under the team lock. Details-only edits need only the team lock.
A database insert/update capacity trigger locks the team and checks configured maximum as a backstop. Future admission services must still follow anchor-first ordering and return explicit full-team errors. Minimum is readiness only; succession sorts joined_at then membership UUID. Empty teams are deleted in the departure transaction. Audit covers create/edit/leave/removal/transfer/deletion and is protected against UPDATE/DELETE/TRUNCATE by triggers. Privileged DDL/migration-role separation remains a deployment concern; triggers are not protection against a superuser disabling them.
M2 audit visibility default (not a competition requirement): current or former participants may read that team's history. Current membership or immutable actor/USER-target evidence authorizes access; strangers cannot. This supports retained history after deletion without exposing private profiles/emails. Team/roster/board reads require authentication and expose only public display names/member IDs. Audit pages default 50/max100; board uses UUID keyset pages default50/max50. Hackathon listing is bounded at 100. No deadlines/configuration-management or inactive-event admission policy is invented; active is informational in M2.
An empty, deterministic TeamForge Demo event is inserted only if its ID is absent; existing event/user/team data is never replaced. This is not the required 10000-user/2000-team seed, which remains future work. Team fields: name 1–120 non-control characters, description <=2000, desired skills follow existing normalized tags (max20, <=40 characters each).
M2 create retries while membership exists return 409 and cannot leave duplicate/orphan teams. Persisted same-key replay, different-payload conflicts, retry-after-deletion behavior and the 50-contender race are explicitly NOT implemented/proven here; they remain M3 acceptance work. No idempotency header is required or acknowledged by the M2 contract.

## M1-B approval and implementation record — 2026-11-09
The user explicitly approved local email/password with secure hashing and server-managed sessions. This supersedes the unresolved OIDC choice below; no external provider is needed for this slice. Deployment selection remains open.
Registration creates account and default UTC profile in one transaction and leaves the participant signed out. Spring Security's form login rotates session ID and persists the security context; logout invalidates the session. BCrypt cost 12, passwords 12–72 characters and at most 72 UTF-8 bytes; emails are validated ASCII, normalized lower-case and database-unique. DTOs never expose password hashes; principal credentials are erased after authentication. Email verification/reset are not implemented in M1-B.
Production cookies remain Secure/HttpOnly/SameSite=Lax. Explicit local profile permits HTTP cookies only for local development; Start-Backend.ps1 -LocalHttp selects it. Session-backed CSRF covers registration/login/logout/profile changes; client retrieves a fresh token before mutations, including after login/logout rotation. Authentication POSTs share a bounded per-IP limiter (30/minute, 10000 live keys); no forwarded IP trust or external infrastructure. Multi-instance coordination remains future deployment work.
Profile defaults: display name 1–80 non-control characters; named IANA/tzdb zones, UTC initially; up to 20 normalized ASCII skill tags of 1–40 characters; up to 28 non-overlapping same-day weekly HH:mm windows. Empty arrays clear collections; absent/null PATCH fields stay unchanged. Unknown JSON fields are rejected. Profile identity comes exclusively from the session; optimistic version conflicts return 409.
V2 adds users/profiles/profile_skills/profile_availability; V1 is unchanged. The earlier shared skills catalog was proposed only; normalized profile tags are sufficient here, with taxonomy deferred. No team/event-management/SSE/suggestion behavior was added.
M1-A was reverified before work: Java 21 verify and executable packaging passed (five tests, no skips), plus existing backend/readiness/frontend-proxy GETs returned 200. Earlier missing-JDK/plugin blockers are resolved. For M1-B, unchanged cached artifacts were copied to ignored .tmp/m2-local to avoid read-only JAR AccessDeniedException. An overridable teamforge.build.directory isolates verification from IDE-generated error stubs observed in shared target output; default Maven/CI output stays target. No dependency version changed.
