# Architecture

## M8-A board read optimization
The read-only REPEATABLE READ board transaction still validates the event and derives authoritative counts from PostgreSQL. It now uses the returned native `sort_name` for continuation, avoiding a redundant query. One board SQL statement walks event/filter/keyset-eligible ordered candidates and uses indexed LATERAL roster counts before capacity/readiness filtering and LIMIT. A MATERIALIZED page bounds subsequent team/profile joins. These are server-side index probes, not per-team network/API queries; no denormalized counter/cache or new membership path. Existing min/max/status, C-collation/UUID keysets, sentinel rows,404/auth/privacy semantics remain tested.

Pool10/16/20 direct-service trials favored retaining default10; no datasource setting changed permanently. Actual unchanged100-VU k6 at pool10 passed p9542.566ms. See [phase verification](verification-m8-a-optimization.md) and [load evidence](load-test-report.md), including shared-host limitations. M3 locks/idempotency and V1–V6 remain unchanged; M8-B is not started. Earlier implementation descriptions below are historical where superseded by this section.

## M7 release and security hardening

Optional Maven `web` packaging serves the built React assets from the same JAR/origin; the multi-stage non-root Dockerfile is a portable release recipe, not a deployed/tested image. Hosting remains open. CI uses isolated PostgreSQL and explicit Linux Chrome provisioning; see [CI](ci.md).

## M5 discovery/SSE/matching implementation
Latest user scope moves live delivery into M5 and reserves M6 for later visual polish. This supersedes older milestone labels and statements that SSE/matching are absent. Admission locks and persisted key/replay semantics remain unchanged.

BoardQuery performs event validation and one grouped roster/profile query (plus one constant cursor-key lookup on name-paged responses) inside REPEATABLE READ. No per-team API/database fetch loop or denormalized membership count. Exact desired-skill/open-capacity/readiness filters apply before page limit. Stable id order and lower-name/UUID order use keyset cursors. V6 only adds GIN desired-skills and event/lower-name/ID indexes; existing roster/event indexes support joins. Counts always derive from committed rows. Cross-request page membership may change under mutation; refresh resets pagination.

TeamStore.audit registers a per-transaction/event-coalesced EventStreamHub synchronization. Only afterCommit enqueues invalidation; rollback/retry failure and stored idempotency replay publish nothing. All create/edit/admit/leave/remove/succession/delete/invite/request mutations already audit through this path; cleanup shares that event. Notification publication adds no database lock/query and occurs after the domain transaction commits. Best-effort, in-process only; process crash between commit and callback loses notification. Every connection/reconnect sends ready and requires REST reconciliation; frontend also refetches every30s. No durable replay, broker or cross-replica bus.

Each bounded subscription has a16-entry queue and one Java21 virtual writer thread; publisher never performs socket writes. Queue overflow closes the subscriber. Single daemon scheduler enqueues15s heartbeat comments; errors/completion/timeout remove the subscription. Per-user2/global10000 admission bounds; configurable30min emitter timeout. Writer validates the existing session on every send, including heartbeat, and ends expired/logout sessions. SSE holds no database transaction/connection. Async servlet dispatch is allowed after the initial authenticated endpoint check; mutation CSRF and authorization remain intact. Transport write-blocking and proxy shutdown behavior still need deployment/load verification. Team stream alias carries only generic event-level refresh hints, so no private team workflow identifiers leak.

SuggestionService uses a committed snapshot, current leader check and indexed event-membership exclusion, bounded10001 candidate IDs, batched profile/skill/availability reads in one SQL statement, and a bounded top-limit heap. Team common availability is a seven-day minute bitmap; actual IANA conversion handles DST. Detailed formula/privacy/defaults are in api-contract.md. No private raw profile data is returned. Ranking is a read-time advisory snapshot; membership eligibility and authority are rechecked only by the unchanged admission transaction. Requests/recommendations confer no joining authority.

React has one EventSource per active event, cleaned on change/unmount. Ready/reconnect and debounced invalidations refetch REST; periodic30s reconciliation bounds missed events. Session checks on errors/polling handle401. Background refresh preserves selected team and in-flight creation/admission form keys; workflow lists and suggestions refetch on revision. Filters reset page cursor and sorted pagination deduplicates IDs. No frontend test runner/dependencies are introduced; build/typecheck plus HTTP/proxy evidence are recorded separately from browser/runtime coverage.

## M4 implemented workflow adapters (current)
AdmissionWorkflows exposes authenticated invitation/request operations through AdmissionController; both successful entry workflows call MembershipAdmissionService. The only roster insertion primitive remains shared with creation. There is no independent invitation/request membership writer.

JOIN and ACCEPT first claim their caller-scoped outer idempotency key, then the shared admission key; both keys are acquired before domain locks, in a fixed outer-to-inner order. These operations use distinct inner scopes (INVITE_ADMIT/REQUEST_ADMIT), preventing cross-workflow collisions. READ COMMITTED locator reads identify team/applicant only. Next: ensure/lock applicant anchor FOR NO KEY UPDATE, lock destination team FOR UPDATE, then lock/validate invitation or request. Invitation authority requires actor==target and valid nonrevoked database-time expiry; RequestApproval requires the locked team's current leader and matching pending applicant request. Append rechecks event exclusivity and capacity. RequestResolution accepts the source and closes other event-pending requests while still holding the applicant anchor. Creation also closes pending requests.

Request creation, withdrawal and decline follow applicant anchor → team → subordinate records. Request creation on full teams is allowed; failed full acceptance keeps PENDING. Duplicate pending creation returns the existing record. Terminal requests cannot transition again. Cross-team pending cleanup touches only request rows and audit snapshots, in ordered request IDs; it does not lock other teams or acquire another applicant anchor. Competing decisions for one applicant serialize at the anchor. Other-team deletion may wait on request rows but cleanup never waits on that team's lock, avoiding a cycle. All transitions/audit/outcomes roll back together.

Rotation needs only team → invitation locks. Redemption uses applicant → same team → invitation, so rotation cannot invert subordinate/team order. Team deletion cascades active invitations/requests while preserving audit/idempotency. Team leave/removal/succession already use the same team lock; old leader authorization becomes invalid after transfer commits. Replay is a historical response retrieval for the original caller, not a new authority decision.

Nested transaction runners now propagate retryable SQL exceptions to the owning root runner instead of converting them prematurely. Only the root retries the entire outer-key + inner-key + domain transaction after rollback; counters are recorded once at that root. Existing bounds and unknown-outcome behavior remain. A real nested-redemption timeout test checks recovery. No retry of partial fragments or extra infrastructure is introduced.

Redemption has a bounded account/IP security filter after authentication/authorization, with CSRF still active. SecureRandom256-bit codes are hashed before persistence/fingerprinting. Plaintext is returned once and retained only in ephemeral UI state; no retrieval/storage/logging/audit path. Audit history permission now requires membership evidence, so merely submitting/deciding a request does not grant access to the team's full history. SSE and suggestions remain unimplemented.

## M3 implemented admission and idempotency (current)
This section supersedes M2's deferred-idempotency statements below. See [verification](verification-m3.md), [database](database-design.md) and [contract](api-contract.md).

MembershipAdmissionService is the production entry point for future admissions. Its internal Command contains team, target participant, server-derived actor, a sealed trusted authorization context and key. The implemented LeaderApproval context verifies the current leader under the team lock. It is not an HTTP DTO or public direct-join endpoint. M4 must add validated invite/request consumption within the same transaction; no invitation/request workflow exists yet. Creation uses the service's shared membership append primitive inside its keyed creation transaction.

Root mutations use READ COMMITTED. Lock order: claim the caller/operation/key idempotency row when applicable; ensure and lock affected event/person anchors FOR NO KEY UPDATE; lock teams FOR UPDATE; then future invitation/request rows. Multiple anchors/teams must be ordered by ID. Discover identifiers first and revalidate after locks. Never acquire another participant anchor after a team lock. Internal callers joining an outer transaction must supply a writable READ COMMITTED transaction; all production entry points own the root transaction. No event-limit management endpoint exists; changing event limits concurrently is outside this protocol.

The anchor serializes one person's competing teams; the team lock serializes capacity checks, inserts, removal, departure and succession. Recheck membership, capacity and current leadership after locks. Earliest remaining joined_at/member UUID determines succession. Creation/member insert/audit, admission/audit and departure/transfer/deletion/audit each commit atomically. Event-aware unique/FK constraints, deferred leader membership and the existing capacity trigger remain final guards. Retained audit and idempotency records do not cascade with deletion.

IdempotentMutations claims and locks a persistent key before executing domain work. Canonical request fingerprints distinguish content changes; complete response JSON and status commit with the mutation. Duplicates wait and replay without reapplying effects, including after deletion. Failed work rolls back the claim, mutation and audit. Normal IN_PROGRESS is uncommitted; an anomalous committed IN_PROGRESS returns conflict and is never stolen. Records have no automatic expiry/cleanup in M3. A future retention policy requires review before removing the replay guarantee.

MutationTransactions applies lock_timeout=5s, statement_timeout=15s and transaction timeout=30s, configurable through environment-backed Spring properties. At most three whole-root attempts retry SQLSTATE 40P01, 40001, 55P03 or 57014 after rollback. Joined transactions are never retried as fragments. Exhaustion returns REQUEST_BUSY; connection SQLSTATE 08 returns OUTCOME_UNKNOWN without blind retries. Keyed callers retry the same key after ambiguous outcomes. Metrics count conflicts/retries by SQLSTATE. Read snapshots retain REPEATABLE READ. SSE remains future work with reconnect and authoritative refetch; no uncommitted notification is published.

## M2 implemented lifecycle (current)
teams.api/application/persistence is the new module. TeamStore uses JdbcTemplate through the existing transaction manager; services own transaction boundaries. Creates/leaves/removals use READ COMMITTED with participant anchors FOR NO KEY UPDATE before team FOR UPDATE. Details-only changes take the team lock. Authority and membership are rechecked after locking; no client leader/actor field is accepted.
New-team creation writes team, creator membership and audit atomically. Leave removes the member, selects earliest remaining (joined_at,id), transfers leader if needed, or deletes the final active team; all audit events commit in that same transaction. Database uniqueness/event-aware FKs/deferred leader FK/capacity trigger remain the final integrity guards. Succession never requests another participant lock after the team lock. Anchor key-share compatibility avoids unnecessary FK lock cycles; no deadlock-free or 50-contender claim is made without M3 tests.
Repeatable-read snapshots keep multi-query team/roster/my-team responses consistent. Board summaries aggregate counts without per-team roster queries. All dashboard/roster reads require authentication; audit reads additionally verify current/former participant evidence and remain available after active deletion. No email/password/profile-private data is exposed by team endpoints. Audit rows reject update/delete/truncate and retain snapshot identifiers.
The React dashboard reuses the typed client and fresh CSRF-per-mutation flow. It displays event limits/readiness, team details/members/leader, create/edit/leave/removal controls and authorized retained history. Profile/login/logout remain available. No direct joining, SSE, suggestions or new infrastructure.
Future M3 operations must reuse these anchors/locks and add persisted idempotency before claiming replay safety. Configure no event-limit changes concurrently through an API in M2; no such management endpoint exists. PostgreSQL lock compatibility reference: https://www.postgresql.org/docs/current/explicit-locking.html.

## Transaction and lock protocol (proposed)
Persist event-participant rows before membership actions. Lock affected participant rows in ascending ID order, then team rows ascending ID, then request/invite rows. Discover IDs before locking and revalidate after locks; restart on changed assumptions. Never acquire a participant lock after a team lock.
All create/join/accept/remove/leave paths use this protocol. Leader leave locks its participant and team; concurrent acceptance locks applicant and team, then checks current leader under the team lock.
Check membership uniqueness, capacity and authority after locks. Team creation inserts creator membership atomically. All roster changes lock the team; serialize capacity check and insert. Unique event/person membership remains the final guard.
Removal/leave updates succession or deletes active team state in the same transaction. Audits commit with domain changes. Deadlocks roll back; bounded retry only for recognized transient failures.

## Idempotency (proposed)
Require Idempotency-Key for mutations, especially create/join/accept. Unique actor/operation/key, canonical payload hash, persisted response and resource ID. Claim key before domain locks; concurrent duplicates wait/replay. Different payload returns conflict. Successful outcome and mutation commit together. Retain creation keys through event lifetime, including deleted resources. Failure-retention policy remains open.

## Audit and SSE
Audit actor/action/database timestamp and relevant identifiers in the mutation transaction. Keep audit references valid after team deletion without cascading audit removal.
Publish minimal event/team invalidations after commit. Board/team clients refetch authoritative state on events and every reconnect. SSE has no durable delivery guarantee; periodic refetch bounds missed updates (interval proposed 30 seconds). Authenticated subscriptions enforce visibility and session expiry.
Single-instance delivery is proposed only. Multiple replicas require a reviewed cross-instance notification mechanism. Provider, hosting, availability and recovery targets remain open.


## Review clarifications
Approved security uses Spring Security server-managed sessions with secure cookies and CSRF protection; provider remains open. Approved idempotency persists outcomes and rejects same-key/different-payload reuse. Authentication and authorization precede replay so a key is not an access bypass.
All admission paths (creator membership, invite redemption and request acceptance) use the same participant/team lock protocol. Removal locks the target participant before the team; only the current leader can remove another member. Succession is selected under the team lock; no successor participant lock is acquired afterward. The new leader must still be a member when the transaction commits.
Proposed pending-request cleanup: discover all affected team IDs before locks, lock them in ascending order after the participant row, revalidate and restart if discovery changed; only then lock/update requests. Request creation/withdrawal also locks the applicant first. Do not acquire additional out-of-order team locks during cleanup. Concurrent leave/accept/remove rechecks authority after locking. Last-member deletion, dependent cleanup, audit and idempotency outcome are atomic.
Audit history is immutable; application role must not update/delete audit rows. Team deletion preserves snapshot identifiers without a cascading team FK. SSE emits no uncommitted state.
